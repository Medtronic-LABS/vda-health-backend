# Medical report retention and deletion

The upload endpoint stores the source file, extracted text, structured facts, and a short explanation in `medical_reports`. Access requires the authenticated mobile patient, tenant, active session, and `record_read` consent. Consent withdrawal blocks report access; it does not itself delete the report.

Every new turn sent with `report_id` has `conversation_turns.reportId` provenance. Its question and answer are not retained in general conversation history, even when general conversation retention is enabled. Report turn HTTP responses are never cached in Redis by the idempotency interceptor. Other turns keep their existing retention and retry behavior.

Deleting a report locks the owned report, clears the linked turn text and report reference, marks those turns `REDACTED`, and deletes the report in one database transaction. The Android UI removes its in-memory linked questions and answers after the delete succeeds and suppresses a late response from an in-progress question. Non-sensitive audit events remain; their `entityId` may retain the opaque report UUID for accountability, but their details do not contain extracted values.

Limits: turns created before provenance was introduced cannot be reliably identified from their text and are not changed by this migration or deletion. A report response cached by an older backend may remain in Redis until its configured TTL expires, although new code skips replay for report turns. PostgreSQL backups, WAL archives, replicas, device screenshots, and external AI provider retention are outside this application transaction. Deleting the live row does not purge those copies. Questions in which a patient manually types report values without choosing a report are ordinary patient input and cannot be linked to an uploaded report safely.

Product and regulatory owners must approve a report retention period, backup and WAL deletion schedule, treatment of historical untagged conversation data, and any policy that would allow report-derived chat retention. No period is assumed here. Apply and review both the report-table migration and the additive turn-provenance migration before enabling this code against a database; do not backfill old turns by text matching.

Replacement: the additive `1727001200000-AddMedicalReportReplacement` migration adds category, current state, and pending replacement linkage. It retains all existing rows as uncategorized current reports. For evidence-backed blood glucose, HbA1c, or combined glucose/HbA1c categories, a new upload remains pending while an older current report exists. The authenticated patient must explicitly confirm the replacement. A database transaction changes the old row to an earlier version and the new row to current under a patient/category lock; a partial unique index enforces one current row per known category. Earlier source files and extracted facts stay patient-scoped and accessible as versions. Uncategorized reports are not silently treated as the same category or auto-replaced. Product and regulatory owners still need to decide version retention, backup purge, and whether uncategorized reports require manual category review. No automatic deletion or retention period was introduced.

OCR safety: text-layer PDFs can supply independently checkable evidence lines for values and ranges. Image and scanned-PDF uploads remain viewable as originals, but their AI-only text and values are not exposed or used to classify the report. A synthetic blank image previously elicited a plausible fabricated glucose value from the multimodal provider, so image-only extraction is disabled until an independent OCR verification or a reviewed human confirmation path exists. Existing image-derived rows uploaded before this change are not rewritten by the migration; their displayed facts should be reviewed before production enablement.
